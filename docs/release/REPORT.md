# Release pipeline report

Live record of the CI/CD and release-automation implementation for GameHandler,
including every real GitHub Actions run, the failures observed, the fixes made,
and the final verification results.

## Runners

| Purpose | Label | Architecture |
| --- | --- | --- |
| CI gate, x86_64 release build | `ubuntu-24.04` | x86_64 |
| CI native ARM build, aarch64 release build | `ubuntu-24.04-arm` | aarch64 |

Both are GitHub-hosted runners, free for public repositories, and used for
**native** builds — no QEMU, no cross-compilation. Each job asserts
`uname -m` matches the expected architecture before building.

## Workflows

| File | Trigger | Jobs |
| --- | --- | --- |
| `.github/workflows/ci.yml` | push to `main`, pull requests, manual | `gate` (fmt/build/clippy/tests/metadata via `scripts/ci.sh`), `build-aarch64` (native compile + `file`/`readelf` arch check) |
| `.github/workflows/release.yml` | push of `vX.Y.Z` tag, `workflow_dispatch` with `tag` input | `validate` → `build` (matrix x86_64 + aarch64) → `publish` |

Release job graph: `validate` checks tag↔version consistency
(`scripts/release-check.sh`); `build` produces
`gamehandler-vX.Y.Z-linux-<arch>.tar.gz` and `…-<arch>.flatpak` per
architecture, verifies each bundle's OSTree ref, and smoke-tests
`flatpak run … --version`; `publish` merges both architecture artifact sets,
regenerates `SHA256SUMS`, re-verifies the complete set, creates a **draft**
release, uploads all five assets with `--clobber`, reads the release back to
confirm every asset is present and non-zero, and only then publishes.
`fail-fast: false` keeps a failure in one architecture visible without
cancelling the other leg; `publish` cannot run unless both legs succeed.

Third-party actions are pinned by commit SHA
(`actions/checkout`, `actions/upload-artifact`, `actions/download-artifact`,
`Swatinem/rust-cache`). Permissions: `contents: read` top-level;
`contents: write` only on the `publish` job.

## Version sources

- Workspace `Cargo.toml` (`workspace.package.version`) — canonical
- `crates/app/Cargo.toml` inherits workspace version
- `gamehandler/__init__.py` (Python reference implementation)
- Newest `<release>` in `data/com.goshapps.GameHandler.metainfo.xml`
- Git tag `vX.Y.Z`

`scripts/release-check.sh` fails the release if any disagree.

The x86_64 Flatpak is ~15× the aarch64 one because it bundles the Wine base
app (`org.winehq.Wine`), the i386 compat extension, and DXVK — none of which
exist for aarch64 on Flathub (see Packaging notes below).

## Flatpak process

`build-aux/flatpak/com.goshapps.GameHandler.json` is the x86_64 manifest:
Freedesktop Platform/SDK 25.08, `org.freedesktop.Sdk.Extension.rust-stable`,
Wine base app + `Compat.i386` + GL32 extension + `--allow=multiarch`, DXVK
runtime module, `osslsigncode`, then the app built offline from
`cargo-sources.json` (generated by the vendored
`flatpak-cargo-generator.py`).

For aarch64, `scripts/package-flatpak.sh` generates a manifest variant beside
the original (so `dir`/`file` source paths still resolve) that drops `base`,
`base-version`, `inherit-extensions`, `--allow=multiarch`, and the
`dxvk-runtime` module — Flathub publishes no `org.winehq.Wine` aarch64 build
and the compat extensions are x86-only. The app itself is arch-independent;
on ARM it can still manage user-downloaded runners, it just cannot bundle
x86 Wine.

Bundles are produced with `flatpak build-bundle --arch=<arch>`, and the OSTree
ref inside the bundle (`app/com.goshapps.GameHandler/<arch>/stable`) is read
back via a scratch `ostree init` + `flatpak build-import-bundle` in
`scripts/verify-release.sh` — architecture is proven, not assumed.

## tar.gz process

`scripts/package-release.sh` stages a deliberate layout (never a blind
`target/` archive):

```
gamehandler-vX.Y.Z-linux-<arch>/
├── bin/gamehandler            (release binary, ELF arch checked first)
├── install.sh                 (installs into $PREFIX, default ~/.local)
├── LICENSE
└── share/
    ├── applications/com.goshapps.GameHandler.desktop
    ├── metainfo/com.goshapps.GameHandler.metainfo.xml
    ├── icons/hicolor/{scalable,64,128,256,512}/apps/…
    └── gamehandler/microsoft-identity-verification-root-ca-2020.pem
```

`readelf -h` asserts the ELF machine matches the target arch before tar'ing.

## Checksums

`publish-release.sh` regenerates `SHA256SUMS` over exactly the four artifacts,
then `verify-release.sh` requires the file to exist, `sha256sum --check`
to pass, and the listed names to be exactly the four expected assets.

### Fixes applied (in order)

1. `scripts/verify.sh`: replaced `paste | bc` with `awk` (`bc` absent on runners).
2. `scripts/verify.sh`: strip ANSI SGR from cargo output before the anchored
   `Compiling` grep — `CARGO_TERM_COLOR=always` on CI made it never match.
3. `ci.yml`: create `build-aux/flatpak/venv` with `aiohttp`, `tomlkit`,
   `PyYAML` for `flatpak-cargo-generator.py`.
4. `release.yml`: `elfutils` (flatpak-builder needs `eu-strip`), `binutils`,
   `file`, `desktop-file-utils`, `appstream`.
5. `scripts/package-flatpak.sh`: emit the aarch64 manifest **beside** the
   source manifest instead of into `target/`, preserving relative `dir`/`file`
   source paths.
6. Manifest: `appstream-compose: false` — the metainfo is already validated by
   `appstreamcli validate`; compose's extra value is embedding downloaded
   screenshots, which fails on runner appstream 1.0.2.
7. `ci.yml`: `fetch-depth: 0` for the gate (traceability tests need history).
8. `ci.yml`: `cargo fetch --locked` before the gate so `cargo metadata
   --offline` sees the whole lockfile graph.
9. `release.yml`: official `ppa:flatpak/stable` → flatpak 1.18.x, which
   understands `--device=input`/`--device=usb` (stock noble 1.14 does not).
10. `release.yml`: `librsvg2-common` — gdk-pixbuf SVG loader required by
    flatpak export icon validation.
11. `crates/core/src/installers/signature.rs`: also resolve the Authenticode
    root under `$XDG_DATA_HOME/gamehandler` / `~/.local/share/gamehandler` so
    tarball installs actually find the staged `.pem`.
12. `scripts/publish-release.sh`: regenerate `SHA256SUMS` **before** verifying
    (the verifier requires it), and strip `^{}` peeled refs when picking the
    newest tag for `--latest` (`v0.8.0^{}` otherwise sorted last and forced
    `--latest=false`).

## External blocker: account billing lock

After run 35054216058, GitHub locked Actions on the account:

> The job was not started because your account is locked due to a billing
> issue.

Every subsequent run — including `workflow_dispatch` retries — failed the same
way before any job step executed. Git pushes, tags, releases, and artifact
downloads are unaffected; only job execution is gated. **The account owner
must resolve billing for future CI/release runs to execute.**

Because the lock blocked the final x86_64 leg (which had already passed every
step except flatpak export, and whose only defect — the missing SVG loader —
was fixed in 17c0f73), the v0.8.0 release was completed locally with the
identical scripts the workflow runs:

- aarch64 tarball + flatpak: **the actual CI-built artifacts** downloaded
  from run 35054216058's `release-aarch64` upload.
- x86_64 tarball + flatpak: built locally on this x86_64 host by
  `package-release.sh` / `package-flatpak.sh` from the same commit.
- Verification, checksums, draft→upload→read-back→publish: all performed by
  `scripts/publish-release.sh`, exactly as the workflow's publish job does.

The tag `v0.8.0` points at `8cc7995`, which contains the corrected publish
script, so a `workflow_dispatch` rerun on this tag is consistent.

### What remains unproven by CI itself

The x86_64 release leg has not yet executed end-to-end on the runner with the
`librsvg2-common` fix in place, and the `publish` job has not executed on a
runner — the billing lock stopped every attempt before job start. Both are
scripted, deterministic, and were exercised locally by the same commands the
YAML invokes. Once billing is resolved, `workflow_dispatch` on `tag: v0.8.0`
(or any new `v*` tag) exercises the full pipeline end-to-end.
